This establishes that the official GitHub image archive and selected Docker Hub platform image describe the same config/rootfs. The image contains `conf/version=4.3.0` and 4.3.0 application JAR names. This is enough to inspect the artifact itself, but not to claim every path in the full application was audited.

## License and account / datasource evidence

The image root `LICENSE.txt` is byte-identical to the v4.3.0 source repository `LICENSE.txt` (SHA-256 `a714b40a28d8cefd070eb0b62e976edf3e85f3304ff4097971453da778ef7844`), Apache-2.0. The image also contains third-party notices and a separate Oracle Free Use Terms and Conditions notice. The bundled Oracle JDBC driver family is version 23.26.2.0.0. The Oracle notice is separate from CloudDM's Apache license; Oracle's published FUTC permits internal business use subject to its terms, with redistribution conditions. This review does not audit every dependency, database-server entitlement, or any prior commercial agreement.

The public pricing evidence has changed since the old index result: current official [pricing URL](https://www.cdmgr.com/en/pricing) now resolves to product information saying CloudDM is fully open sourced, with no 10/5 pricing table. The prior search-index result “10 datasource / 5 accounts” is stale evidence and is not treated as current pricing. The v4.3.0 source has `checkSubAccountCount()` commented out in `RdpUserServiceImpl.java:634–640` `addSubAccountCheck`; the selected internal/bind account paths call this helper. In the selected released binary, static disassembly of that helper/callers likewise shows no call to the count-check routine. Spot-checked UI create controls in `ui-subaccount-index.vue`, `ui-datasource-info.vue`, `ui-datasource-view.vue` and API binding `ui-user-api.js` show no explicit 5/10 limit gate in those views. The reviewed datasource creation methods (`DmDsController.java:183–196`, `DmDsWebServiceImpl.java:305–348`) require the management permission and persist the datasource; the selected binary path has no active 10-datasource counter call. A narrow UI spot-check of the sub-account create view, datasource form/view and user API bindings found no explicit 5/10 limit check in those controls. These findings remove the old selected-path cap hypothesis for 5 accounts/10 datasources. They do not prove unlimited entitlement or absence of counters in every import/API/global-hook path, nor test 50 datasource / 20 account capacity under load or every possible UI entry point.

Decision: public OSS/self-host rights for the reviewed CloudDM application code and selected image scope are supported; current public evidence does not substantiate the old 10/5 cap. Do not make a vendor response or another static source survey a prerequisite. Any prior commercial agreement or support entitlement is not inferred from the open-source code license; verify it only if the organization has such an agreement or needs paid support. It is not a default blocker to self-hosting the reviewed Apache-2.0 application. Unreviewed global paths and runtime scale remain adoption limits, not reasons to re-run completed public research.

## Migration behavior: exact default path and remaining gap

A pinned full-source search for explicit Java `setUseCompile` assignments found only the request clone/default and `ActionServiceImpl` interactive browse compile trigger. That interactive browse path enables compile for procedure/function/view inspection; it is distinct from the approval ticket executor. The selected v4.3.0 source and selected release JAR bytecode agree on the Oracle ticket compile default: `QueryRequest.useCompile` defaults false (`QueryRequest.java:58`); `OraDsPlugin` registers `OraSessionSpi`, which inherits `RdbSessionSpi.createQueryRequest` (`RdbSessionSpi.java:65`) and does not override it. Reviewed `AutoExecServiceImpl` creates a fresh request and copies request fields including SQL/args/types, but does not set `useCompile`. The separate `ActionServiceImpl.java:429` explicit setter is for interactive browse compile, not the approval ticket path. Thus the reviewed default approval-ticket execution does not turn on the Oracle compile/`ALL_ERRORS` gate. Oracle compile diagnostics can emit Error and the auto-exec item path can throw on Error when compile mode is enabled; the job runner/provider and approval state services propagate a failed job to failure state. That conditional error path does not repair the default-off gate, and compile helper coverage/owner-name/object-type correctness remains insufficiently established for all Oracle object types.

The selected path is consistent in source and binary, but this is a scoped JAR/class comparison, not a whole-image source mapping. Exact source classes and selected disassembly excerpts are pinned in the artifact manifest. The search is limited to explicit Java setter/assignment paths in the pinned full source; it does not claim exhaustive coverage of reflection, generated code or extension code. Existing [`clouddm-release-comparison.json`](clouddm-release-comparison.json) separately records source files byte-identical across older/newer source pins.

CloudDM uses Flyway in `DmFlywayInit.java:47–55` to upgrade its own metadata schema (`dm_update_history`); it does not show Flyway as the customer Oracle target migration engine. The reviewed approval/execution paths establish webhook/commit receipt deduplication but not a durable target migration ID + checksum ledger, target lock, or uncertain-commit reconciliation. Therefore target replay/state and recovery remain distinct gaps, even though the application includes Flyway and has webhook idempotency.

## Decision and effort implications

**Current CloudDM v4.3.0 is NO-GO as the sole/native Oracle migration executor for this brief.** The account/license preflight is closed with scoped public evidence; it is not the reason to block. The decisive issue is default execution without the Oracle compile-validity gate, plus no established target migration ledger/checksum, concurrency guard, or uncertain-commit reconciliation. Do not run the former blind INVALID/replay POC against the unchanged image. Reopen only for a supported build/config delta that explicitly enables complete object validity checking and supplies target-state/recovery behavior. If such a supported delta appears, a narrow regression is still required before any wider POC.

This finding does not reject CloudDM as a Category A workflow/governance UI; inventory, permissions, approval UX and operation-scale fit at 50/20 remain separate runtime questions. The brief's primary goal remains a qualifying self-hosted platform. ODC remains a governance/front-end comparator with source-path gaps; its source pin was checked against current public HEAD/tag listings, but its runtime image is not source-mapped. CI + Flyway remains a secondary, optional composition and is not selected or a substitute for the Category A objective.

The ranges below are expert scope estimates, not spent effort, approved budget, or commitments. POC and operational MVP are distinct; ranges have low confidence until Oracle versions, release scope, existing CI/IDP/secrets and maintenance capacity are known. The older root report's Jenkins + Flyway POC estimate of 5–10 person-days and operationalization estimate of 20–40 person-days assumed existing CI, identity, Git, secret storage and infrastructure; these remain the proper broader implementation reference. The 3–5 PD composition figure elsewhere is only feasibility/design, not a POC.

A 50-instance estate is not a command to run every script on all 50 DBs: select an approved target set per application/release, inspect each target's current state, bind one frozen artifact to that set, execute bounded waves, and stop promotion on any failed/uncertain/applied-but-invalid target. Existing DBeaver/Flyway history has not been measured, so no time-savings claim is made.

## Reproducibility boundary

The archive and registry blobs were hash/size checked; JAR disassembly and source inspection were static. No product, SQL, benchmark, DB, deployment, license server, or 50/20 load test was run. Public source/image inspection closes the feasible public-artifact gate. Remaining runtime, exact contract entitlement, production Oracle version, release-time/DBA baseline, existing CI provider, budget and maintenance capacity are decision inputs; they do not block completion of public research.
