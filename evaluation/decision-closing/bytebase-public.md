# Bytebase public evidence for the decision close

**Research date:** 2026-10-07  
**Branch:** public documentation and source only; no vendor contact, quote, trial, deployment, or Oracle execution.  
**Current release pin:** Bytebase `3.23.0`, tag commit `c8188c635465321ff930c97200742a96ef653144`, released 2026-09-24. The tested historical build remains `3.22.1/FREE`, commit `a85f6cb4195299995e8554303550d672d5093e1d`; these are different artifacts and evidence must not be conflated.

## Decision impact

Bytebase remains the strongest integrated Architecture A comparator, but the public record does not establish a complete native closure for the post-execution Oracle verifier and ordered-promotion requirements. First decide whether the plausible inline PL/SQL failed-task gate can serve as an acceptable control and be supported/enforced across UI/API paths; if not, Bytebase is not closed without a supported product interface or owned extension. Enterprise publicly advertises the needed capacity, approval, audit, and external-secret features, while Community is too small for a 50-instance plan. A quote can establish commercial feasibility after the control path is acceptable; a quote by itself does not justify an Enterprise POC or purchase.

Do not promote Bytebase to the selected solution from public evidence. The 3.22.1/FREE Oracle POC has four historical FAILs (including INVALID-object success and premature promotion), three BLOCKED, and seven NOT_RUN; Enterprise entitlement cannot be assumed to change executor correctness. No public release note or inspected current source establishes that the particular historical FAILs are fixed, and no current-release Oracle RUNTIME result exists. A plausible native workaround is a final PL/SQL verifier in the same task that raises an Oracle application error if required objects are INVALID; successful PL/SQL blocks are supported by the historical lab, but propagation into failed-task status and prevention of downstream rollout still require a current Enterprise POC. This is a designed SQL gate, not a documented first-class verifier hook. Current rollout docs describe gated stage progression, but the historical early-promotion FAIL and a bounded API-handler inspection do not establish that approved UI/API paths enforce verified-predecessor ordering. Treat both task-level error gating and stage-order enforcement as POC entry gates. Also cover approval identity, crash/restore, actual 19c/21c/RAC topology, and operational ownership. No commercial or implementation estimate is inferred.

## Publicly verified product and estate fit (DOC)

The current [pricing page](https://www.bytebase.com/pricing/) lists Community as free with up to **20 users and 10 database instances**; Pro at **$20/user/month**, custom users and 10 instances; and Enterprise as contact sales with custom users and custom instance counts. It places custom approval workflows and external secret manager under Enterprise, and audit log on Pro (7-day retention) and Enterprise (unlimited retention). HA is an Enterprise add-on. Thus 50 Bytebase-counted database endpoints exceed Community and the 10-instance Pro cap; twenty human users fit Community's stated count, but that does not grant the required controls. A public price for a 50-endpoint/20-human Enterprise deployment is not published. No quote, service/support terms, HA entitlement, license measurement or renewal terms have been verified.

The product's [Instance concept](https://docs.bytebase.com/concepts/instance) says one Bytebase Oracle Instance represents an Oracle server/service selected by service name or SID; a Bytebase Oracle Database represents an Oracle user-owned schema. One endpoint can expose multiple schemas. This is not the same thing as counting Oracle RAC nodes/instances, services, PDBs, schemas or release targets one-for-one. The public [pricing page] defines a database-instance ceiling, but does not spell out billing treatment for RAC aliases, duplicate routes, standby endpoints, or project-scoped registrations. Map every real service/SID and schema to Bytebase's registered instance/database records, and obtain written confirmation of counted resources before quote comparison. Seat pricing is stated as users; the public page does not say whether service accounts/workload identities consume seats or how they are excluded. Verify this in the written quote/entitlement schedule. At 20 human users, service principals are a separate unresolved count.

The official [supported databases matrix](https://docs.bytebase.com/introduction/supported-databases) lists Oracle **11g and above** for RDBMS workflow support, and the [Oracle schema migration page](https://www.bytebase.com/databases/oracle/schema-migration/) lists on-prem editions, Autonomous, Exadata and cloud-hosted Oracle destinations. These are vendor compatibility statements, not a certification of the estate's Oracle 19c/21c versions, RAC, TCPS, character sets, grants or 26ai workload fidelity. The historical lab was 26ai EE only. The current Go source at the 3.23.0 pin uses `github.com/sijms/go-ora/v2 v2.9.0` ([go.mod](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/go.mod#L88)); this is the public driver dependency, not a runtime compatibility result.

Bytebase is self-hostable. Official [production setup](https://docs.bytebase.com/get-started/self-host/production-setup) guidance sizes 4 CPU/8 GB for up to 50 users/50 instances and recommends external PostgreSQL for production/HA patterns; [HA docs](https://docs.bytebase.com/get-started/self-host/high-availability) describe multiple replicas coordinated through shared external metadata PostgreSQL and note license enablement. The [upgrade and backup/restore guide](https://docs.bytebase.com/get-started/self-host/upgrade) requires metadata backup before upgrade, distinguishes embedded PostgreSQL data-directory backup (stop Bytebase before copying) from external PostgreSQL clone/restore, and states that in-place downgrade is not supported. This is a credible documented operating procedure, not proof of this team's restore time, HA behavior, or audit/history retention after restoration. The platform's PostgreSQL metadata store is an operational dependency in addition to Oracle.

## Governance, identity, release and rollout evidence (DOC)

The current [Custom Approval docs](https://docs.bytebase.com/change-database/approval) describe condition-based routing and sequential approval nodes. Release 3.23.0 states that the last person to edit a plan cannot approve it when the project setting is off; this setting defaults off for new projects but remains on for existing projects after upgrade ([release](https://github.com/bytebase/bytebase/releases/tag/3.23.0)). This is useful separation-of-duties support, but exact artifact/target/options binding and enforcement across the proposed operating model still require a case-level POC. Historical 3.22.1/FREE approval tests were BLOCKED by edition.

The [Audit Log docs](https://docs.bytebase.com/security/audit-log) say audit is available on Pro and Enterprise and can be queried/exported through UI/API or streamed to stdout. Current pricing states Pro retention of 7 days and Enterprise unlimited. The 3.23.0 release changes audit actor representation from a user-only field to `actor` values for users, service accounts, or workload identities, and describes differences between stored and stdout treatment of refused calls. Audit schema/API consumers must account for that version change. Public audit is workflow-layer evidence for actions through Bytebase; it does not capture direct Oracle paths, so Oracle Unified Auditing remains a complementary control.

The [service-account docs](https://docs.bytebase.com/administration/service-account) describe scoped workspace/project identities using API keys, least-privilege roles, one-time key display, rotation and token-expiry caveats. The current [workload identity docs](https://docs.bytebase.com/administration/workload-identity/overview) describe short-lived OIDC credentials and support a generic issuer; 3.23.0 release notes explicitly add any OIDC issuer and required audience. These authenticate callers to Bytebase, not to secret stores or Oracle.

### External secret managers (SOURCE, Bytebase 3.23.0)

The current pinned [external-secret protocol](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/proto/v1/v1/instance_service.proto#L598-L680) and [provider dispatcher](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/component/secret/secret.go#L12-L30) name four supported stores. The same pin's [plan definition](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/enterprise/plan.yaml#L130-L171) gates `FEATURE_EXTERNAL_SECRET_MANAGER` to Enterprise (also listed as an instance feature). Public marketing currently calls this an Enterprise feature. Provider and auth behavior in the source is:

| Store | Publicly supported lookup/auth path at the 3.23.0 pin |
| --- | --- |
| HashiCorp Vault KV v2 | KV v2 mount (`engine_name`), secret path and password key. Auth is either a Vault token (literal, Bytebase-server environment variable, or Bytebase-server file) or AppRole (role ID plus secret ID supplied literal or from a Bytebase-server environment variable; configurable auth mount path). Vault URL and optional CA/client certificate/key are supported. Source: [Vault client](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/component/secret/vault.go#L18-L164), [protocol fields](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/proto/v1/v1/instance_service.proto#L616-L680). |
| AWS Secrets Manager | AWS SDK default credential chain on the Bytebase server; fetches `AWSCURRENT`, parses `SecretString` as JSON and selects the configured password key. Source: [AWS provider](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/component/secret/aws.go#L17-L55). |
| Google Cloud Secret Manager | Google Application Default Credentials on the Bytebase server (source comments specify GKE credentials, falling back to `GOOGLE_APPLICATION_CREDENTIALS`); reads the `latest` version at the configured secret resource path and returns payload bytes as the secret. Source: [GCP provider](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/component/secret/gcp.go#L19-L56). |
| Azure Key Vault | Azure `DefaultAzureCredential` on the Bytebase server; source lists environment credentials, managed identity, or Azure CLI credentials. Uses configured vault URL and secret name, requesting the latest version. Source: [Azure provider](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/component/secret/azure.go#L14-L51). |

These four providers and their implementation paths are publicly verified. Which provider the estate operates, whether the self-host runtime can use the required identity/network path, policy scope, rotation semantics during a running migration, and secret/log behavior remain untested for this estate. The code has no provider-independent auth abstraction for AWS/GCP/Azure in this integration; it uses each SDK's default credential chain. Do not infer OpenBao compatibility from Vault KV v2 support without testing protocol/auth compatibility.

## License and production entitlement boundary (SOURCE)

At the 3.23.0 source pin, the root [LICENSE](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/LICENSE#L1-L25) grants MIT to code outside the enterprise directories and outside code controlling feature, permission, role, or plan enablement. [LICENSE.enterprise](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/LICENSE.enterprise#L1-L26) says enterprise-covered software may be used in production only under the Enterprise Terms or another agreement and with a valid Enterprise subscription for the correct number of instances and paid plan; development/testing use is allowed without subscription. Thus repository visibility and the MIT subset do not make Bytebase's gated Enterprise features unrestricted OSS, and do not grant permission to remove or bypass license gates.

The pinned [`plan.yaml`](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/enterprise/plan.yaml#L1-L171) internally calls tiers `FREE`, `TEAM`, and `ENTERPRISE`: FREE is 10 instances/20 seats, TEAM 10 instances/unlimited seats, ENTERPRISE unlimited instances/seats; approval workflow and external secret manager are Enterprise-only; audit is limited for TEAM and full for Enterprise. The current pricing page markets Community/Pro/Enterprise, with Pro at 10 instances and 7-day audit. Do not assume tier-name equivalence resolves the contractual product/entitlement mapping; request the applicable marketed plan and counted-resource schedule in writing. This source boundary is separately relevant to the original free-OSS preference: Bytebase can be self-hosted in the free Community tier, but the required 50 endpoints, approvals, external secrets and full audit point to commercial Enterprise use.

Bytebase's [Release concept](https://docs.bytebase.com/concepts/release) describes preserved SQL files as an immutable package; [Rollout concept](https://docs.bytebase.com/concepts/rollout) describes plans progressing through environments, tasks and attempts; the [rollout API](https://docs.bytebase.com/integrations/api/rollout) exposes rollout creation. This supports the central release and multi-target workflow shape. UI Plan checks run before deployment; the docs state GitOps Release-based Plans do not run those UI checks. Current [rollout policy docs](https://docs.bytebase.com/change-database/environment-policy/rollout-policy) describe approval and plan-check prerequisites before rollout creation and manual or automatic execution. Rollout docs say inspect results and verify before continuing to the next environment. These documents describe the intended path, but do not establish an Oracle postcondition check or a supported verifier input to advancement.

There is a plausible SQL-level path: Bytebase supports Oracle PL/SQL change scripts and the historical lab passed ordinary PL/SQL procedure/function/package/block cases. A final anonymous block could query `USER_OBJECTS` or a suitably granted dictionary view and `RAISE_APPLICATION_ERROR` if required objects remain INVALID. If the error is retained as the task result, the failed task can serve as a practical local gate. This is an inference from Oracle execution and Bytebase's task model, not a documented Bytebase verifier feature. DDL already applied would remain committed, the verification query and object filter need estate-specific design, and a fail result must be shown to block all subsequent stages in both UI and API paths.

The current [pinned RolloutService source](https://github.com/bytebase/bytebase/blob/c8188c635465321ff930c97200742a96ef653144/backend/api/v1/rollout_service.go#L789-L945) for batch task execution visibly validates stage membership, task-run permission, required issue approval and same-stage task selection before queueing the run. The bounded handler does not by itself prove the entire product lacks stage-order enforcement, but I did not find a predecessor-success predicate there. Given the historical MODEL-07/GOV-04 early-promotion FAILs, do not treat the public statement of stage-by-stage progression as proof that the exact Enterprise API/UI paths reject a later stage until prior-stage verified success. Generic pricing mentions automatic backup/one-click rollback, but Oracle DDL auto-commits; Bytebase itself notes that failed multi-statement DDL may leave prior statements applied and reversal is a separate reviewed change on its [Oracle page](https://www.bytebase.com/databases/oracle/schema-migration/). Treat generic rollback marketing as engine- and operation-specific.

## Publicly verified post-3.22.1 source/release delta (SOURCE + release notes)

The latest public release listed on the research date is 3.23.0 (release tag commit above), 81 commits after that release were shown on its GitHub page; the latest release is not evidence that later unreleased `main` is deployable. The 3.23.0 release notes list Oracle-specific changes: database-link reads now require access to the linked database and unsupported/unresolvable targets are refused before query; viewing Oracle view/function/procedure/sequence definitions no longer hits an unsupported-engine error, and view definitions include `INSTEAD OF` triggers. These are query/schema-inspection permission and metadata-view fixes. They do not claim to repair the POC's INVALID status reporting, strict altered-content rejection, or stage promotion behavior.

I compared the exact historical 3.22.1 pins with current release source at `c8188c635465321ff930c97200742a96ef653144` for the three existing source-manifest files. The current Oracle driver changed from SHA-256 `039f8e09fa9c67250441097d742877520eee3db71c7d35733e5e84a4be22c9ea` to `f9be79a80101c3eebfd732b094c438a21f82686be18b69f5a0f7e7762097a22a`; visible changes include an Oracle private-database-link ownership check, shared transaction-mode refactoring, and use of the common statement result limiter. Current `database_migrate_executor.go` is byte-identical to the historical pin (SHA-256 `a15c3ef10a3e9bea3ed2690670d169e7614824fc5fced86858be155aa8a8e031`). ## Decision-grade dispositions

**Product conclusion:** Publicly eligible as a commercial Architecture A candidate with strong centralized workflow fit; not eligible as a free-OSS answer at the required capacity/control set. The public first-class verifier-hook question is **RESOLVED_PUBLICLY** as “no supported contract established”: documentation/API and the bounded release-source review show rollout controls, not an external Oracle verifier input. Inline failing PL/SQL remains a plausible native workaround, not a product promise.

**Estate conclusion:** **INTERNAL_INPUT_REQUIRED** before an apples-to-apples quote or architecture selection: enumerate Oracle server/service endpoints, RAC relationships, PDBs, schemas and approved targets; confirm human/API identity counts and actual IdP; identify which of Vault/AWS/GCP/Azure is deployed and how the Bytebase host may authenticate/reach it; confirm host platform, PostgreSQL/HA expectations, and actual Oracle versions/topologies/grants. Public limits distinguish Bytebase instance records from Oracle schemas but do not settle how vendor licensing counts aliases, RAC routes, service principals or project-scoped registrations.

**Commercial conclusion:** **COMMERCIAL_INPUT_REQUIRED** for a written Enterprise quote and entitlement schedule covering 50 counted instances, 20 human users plus service/workload identities, external-secret provider entitlement, audit retention, HA, support/SLA, term and renewal. No public Enterprise price or service-account seat rule is stated. The marketing tiers and source plan enum labels differ; do not infer their legal equivalence.

**POC conclusion:** **RUNTIME_REQUIRED** on the exact intended Enterprise image/license and real deployment shape: 19c/21c/RAC plus TCPS and estate grants; repeat SQL-11, REC-08, MODEL-07/GOV-04 and approval/audit checks; prove PL/SQL verifier errors become task failure and halt progression through UI and every API/automation path; exercise the applicable secret provider's identity, least privilege, rotation and logs; crash between Oracle commit and metadata write; restore/upgrade and validate history/audit. Public compatibility claims and unrelated Oracle release notes do not close these.

Other public hook disposition: **RESOLVED_PUBLICLY**—no first-class external verifier callback/contract identified in public docs or the bounded pinned API/source inspection; **RUNTIME_REQUIRED**—whether the inline PL/SQL path works as a task gate and is enforceable across all dispatch paths. The historical case statuses remain historical evidence; no current Enterprise RUNTIME result is claimed.
