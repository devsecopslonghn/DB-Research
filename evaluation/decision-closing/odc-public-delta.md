# ODC native public-delta decision

**Research date:** 2026-10-07  
**Decision:** **ODC remains HOLD.** Current public evidence does not show a supported release/build/configuration/API/extension delta that reduces the five provisional safety responsibilities to at most two bounded additions. Stop ODC native delta research here; do not repeat the unchanged runtime failures.

## Decision boundary and pins

The historical runtime was **ODC 4.4.1-20260116** (application edition and exact image digest-to-source mapping were not recorded), against Oracle 26ai Enterprise Edition `23.26.4.1.0`. OceanBase CE `4.3.5` was the MetaDB. Results remain 12 PASS / 20 PARTIAL / 5 FAIL / 8 NOT_RUN; this note does not rescore them. The reviewed ODC source pin is [`d517c0f27971642fb0cd7565fd61ab2309875ec3`](https://github.com/oceanbase/odc/tree/d517c0f27971642fb0cd7565fd61ab2309875ec3), and the reviewed client pin is [`273fa3c4cc7d87f942ade231ce9220b98fa595e2`](https://github.com/oceanbase/odc-client/tree/273fa3c4cc7d87f942ade231ce9220b98fa595e2). The earlier path-level survey and hashes are retained in [`odc-source-survey-20261006.md`](../research-round-2/coordinator/odc-source-survey-20261006.md).

The latest official ODC documentation available in this review lists **V4.5.0** and **V4.4.3**. The V4.5.0 release-note content gives `发版时间：2026 年 07 月 31 日` (“release date: 2026-07-31”); **2026-07-31** is my normalization of the page's Chinese date, not a verbatim ISO-formatted date string. Its listed fixes include a login integration approval-flow issue; the note does not describe changes to SQL/target immutability, change admission, execution identity separation, Oracle validity verification, or recovery. V4.4.2's official note records 23 March 2026 and focuses on job management, SQL development, driver/parser performance, data-source expansion, and a security fix. The release notes do not publicly establish closure of the failed acceptance cases; they do not prove that later binary internals lack unlisted changes. [ODC V4.5.0 release note](https://www.oceanbase.com/docs/common-odc-1000000006663615) · [ODC V4.4.2 release note](https://www.oceanbase.com/docs/common-odc-1000000006663623) · [official version selector](https://en.oceanbase.com/docs/odc-en)

The public GitHub repository's tagged releases stop at `v4.3.4_bp2` (`88f845d7520a81fd802b0117e8792c8c42051192`); its current `HEAD` resolves to the already-reviewed `d517c0f27971642fb0cd7565fd61ab2309875ec3`. Thus public docs identify later product versions, but public source does not provide a later commit that can be mapped to the 4.4.1/4.5.0 product artifacts. This is a **source/build mapping gap**, not proof that the binaries contain no changes. The batch feature's serial order, approval routing, project inventory, audit screens, Oracle PL/SQL support, and task logs remain useful product capabilities. They are not evidence for the failed duplicate/checksum, requester/executor, INVALID, or uncertain-outcome controls. Public docs also continue to describe batch tasks as not abortable while a database change process is running, which constrains intervention during a wave; it does not supply a HOLD protocol. [Batch change task process and constraints](https://en.oceanbase.com/docs/common-odc-10000000001510652)

## Responsibility count and conclusion

The current estimate remains **five provisional safety responsibilities**, as defined in the reassessment:

1. **N1 — release/target binding and separated authorized dispatch/promotion**
2. **N2 — version/checksum/deduplication, schema serialization, and admission HOLD**
3. **N3 — Oracle validity verification gate**
4. **N4 — read-only reconciliation and recovery record**
5. **N5 — durable audit and export**

None is publicly shown to be completely owned by a new supported ODC contract/build. Some pieces are native (ticket approval, batch ordering, basic audit/log presentation), but they do not collapse the required safety invariants into two bounded additions. In particular, the release notes do not publicly establish closure of any historical FAIL; the later binary cannot be traced to a reviewed public source commit here, so its unlisted internals remain a runtime/source-mapping unknown.

**Product conclusion:** ODC remains the strongest conditional integrated OSS candidate for existing inventory/workflow and Oracle development strengths, but native production change management is not presently eligible. **ODC remains HOLD.**

**Estate boundary:** This public conclusion does not certify the estate's Oracle 19c/21c/26ai versions, RAC/PDB/schema topology, SQL corpus, Oracle plugin/TCPS adapter, 50-instance capacity, identity policy, or MetaDB/image/support entitlements. Those are internal-input or later adoption questions; none supplies the missing public safety delta.

**POC consequence:** Do not rerun the historical failures and do not start an ODC native POC on the unchanged evidence. Reopen only if a new supported release/build is supplied with an exact source/image mapping and documented control contract that closes immutable binding, cross-request admission/serialization, independent execution authorization, verified Oracle completion and durable HOLD/recovery in no more than two bounded additions. A runtime test would then be a separate, newly authorized regression. This meets the decision-closing mission's stop condition; no ODC research backlog is retained.
