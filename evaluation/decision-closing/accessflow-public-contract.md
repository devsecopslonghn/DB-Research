## Decision

The external API branch is a real, supported governance handoff. It is more complete than the rejected ODC/CloudDM bridge proposals: AccessFlow has a documented trigger → approval → fail-closed gate → execution confirmation → outcome lifecycle, provider wrappers, service-account guidance, human review UI, audit records, and deployment-version views. The code includes those public endpoints and state transitions.

It does **not** establish an immutable Oracle migration authorization or verified Oracle completion contract. AccessFlow authorizes a named pipeline/environment/version request; the caller supplies optional `commit_sha`, `artifact_ref`, `run_url`, and arbitrary metadata. Its duplicate key is `(pipeline, environment, version, external_run_id)`, not a content digest or target set. `confirm-execution` means the pipeline says it is proceeding and changes the request to `EXECUTED`; the later `SUCCEEDED` / `FAILED` / `ROLLED_BACK` outcome is also caller-reported. Neither means Oracle effects, object validity, migration ledger state, or per-target completion were independently verified.

**Product conclusion:** AccessFlow v2.7's external deployment API is a supported human approval/control plane, not a database migration executor. Its workflow, review UI, gate, service-account identity, reporting endpoints and wrappers are real product capabilities; its request model does not bind exact migration content and its `EXECUTED` / outcomes do not attest Oracle state. The deployment API is eligible as Architecture B; native AccessFlow schema execution remains STOP under the current baseline.

**Estate conclusion:** this estate currently reports DBeaver/manual SQL and a previous Git/Flyway CLI attempt. The research has not established that a CI platform is already operated, that AccessFlow is already installed, or who would own the runner, target registry, secrets, recovery and on-call. Those are decision-changing facts, not assumed advantages. If an existing CI service, runner fleet, identity and secrets process already have owners, Git + CI + state + engine may have lower marginal burden. If CI is absent but AccessFlow is already operated for this estate, Git + AccessFlow + a small runner + Oracle evidence may cost less, even though runner correctness obligations remain. If neither is operated, both introduce infrastructure; AccessFlow adds a governance service and cross-system evidence, while CI adds workflow/state/operator code. Therefore current evidence supports RESERVE and does not establish a smaller total solution either way.

**POC conclusion:** no Oracle POC is authorized by this note. If AccessFlow is chosen after the estate ownership comparison, freeze an API-to-runner contract binding exact artifact digest, normalized target IDs, options, request ID, service identity, and retry/claim behavior; then run one bounded integration probe for actor/gate/duplicate confirmation and runner-reported Oracle verification. CI is optional: a protected standalone runner/job can integrate with AccessFlow without a general-purpose CI platform. Keep Oracle RUNTIME as `NOT_RUN` until separately authorized and performed.

## Public API and actor contract

The documented machine entry point is `POST /api/v1/deployment-requests`. It accepts pipeline UUID, environment name, and version, plus optional commit SHA, artifact reference, CI run URL, external run ID, free-form metadata, justification and schedule. Authentication uses an AccessFlow API key mapped to its owning user. The recommended operator setup is a dedicated non-login service account with a `can_trigger` grant on the pipeline and a protected CI secret. A separate human can be recorded through the on-behalf-of header when configured; the service-account identity remains the request submitter. The submitter cannot approve their own request. Reviewers use AccessFlow UI/API review endpoints, and can be restricted by review-plan approver rules.

The submission idempotency constraint is useful but narrower than migration admission: only submissions with `external_run_id` are deduplicated, and the key includes pipeline, environment, version, and run ID. A retry of a given run returns the existing request; it does not prove the same artifact bytes or target resolution, nor deduplicate a second run ID for the same release. The public request shape has no required content digest, resolved target list, engine identity, or execution options digest. The API record is therefore a workflow reference, not itself the approved immutable execution package.

After approval, `GET /api/v1/deployment-gate` returns releasability only when the request is `APPROVED`, no applicable freeze window is active, and any scheduled time has arrived. Gate evaluation fails closed on internal freeze-evaluation errors. The runner then calls `POST /api/v1/deployment-requests/{id}/confirm-execution`; this rechecks the gate at that moment and moves the request from `APPROVED` to `EXECUTED`. This closes the poll/confirm freeze race, but does not provide an exclusive execution claim. The source uses a transaction and a JPA `@Version` optimistic-lock field rather than a row lock or claim/lease. A sequential confirmation after the request is already `EXECUTED` returns its detail successfully by design. Concurrent confirmations may race at the optimistic update, but the API contract does not promise one durable runner lease or prevent a second caller from treating the idempotent already-EXECUTED response as authorization to proceed. `EXECUTED` records confirmation that the external runner proceeded; it is not an AccessFlow observation of Oracle completion.

After the engine attempt, the pipeline reports one outcome: `SUCCEEDED`, `FAILED`, or `ROLLED_BACK`. Identical repeated outcomes are idempotent; a different second outcome conflicts. `FAILED` changes request status to `FAILED`; `SUCCEEDED` and `ROLLED_BACK` leave status `EXECUTED` and populate the outcome field. Rollback can open a human follow-up review. This lifecycle has no outcome enum for `PARTIAL` or `UNKNOWN_OUTCOME`, no per-target result array, and no API proof that the runner checked Oracle object validity, effects, migration history, session loss, or retry safety. An adapter must preserve these states in its own attempt ledger and must never translate an unverified execution into `SUCCEEDED`.

The version matrix and drift UI are useful human views, but current/previous versions are projections advanced on `EXECUTED` and caller-reported outcome. They are not independent Oracle inventory or an authoritative verification ledger. Audit records cover request, review, confirmation and outcome events, but the pinned documentation says a failed audit write is logged and swallowed; do not make AccessFlow's audit trail the only durable execution/recovery evidence without testing the selected release and retention/restore behavior.

## Responsibilities and operator interfaces

| Responsibility | AccessFlow provides at this pin | Still owned by external engine/integration |
|---|---|---|
| Human workflow | Pipeline/environment administration; trigger grants; review routing/quorum; self-approval guard; freeze/scheduled policy; notifications; review and deployment UI | Select a process for artifact construction and make pipeline job failure/timeout behavior match the gate contract |
| Request identity | Service-account API key, submitter actor, optional on-behalf-of human, request/run/version metadata | Preserve exact API request ID and authenticated service identity in the engine attempt record |
| Handoff | Submit, poll, confirm and outcome endpoints; generic curl, GitHub, GitLab and Azure wrappers | Map the approved request to exact bytes, normalized database/PDB/service/schema targets, execution options and one engine run; reject any mismatch before Oracle writes |
| Oracle execution | No execution in this deployment-gate flow; its purpose is to authorize a CI/CD deployment | Restricted Oracle credentials, supported engine/driver, migration history, serialization, exactly-one-writer policy, SQL/PLSQL execution and effect/validity checks |
| Results and promotion | Central request lifecycle and self-reported outcome; environment version projection and drift display | Per-target `SUCCEEDED` / `FAILED` / `PARTIAL` / `UNKNOWN_OUTCOME`; reconcile commit-then-record failures; hold uncertain state and block every later-stage dispatch until verified |
| Recovery and operations | Approval/audit/rollback follow-up workflow and notifications | Named Oracle recovery owner, session/lock investigation, evidence retention, restore test, key rotation/secret access, engine upgrades, target inventory mapping and incident runbook |

AccessFlow's pipeline/environment is an approval namespace, not an Oracle target inventory: the request addresses an environment by name, and generic metadata can carry annotations, but no pinned API invariant resolves instance/service/PDB/schema aliases to stable approved Oracle targets. For this estate, that mapping must be frozen by the runner-side registry or an equivalent owned inventory before execution.

The user-facing workflow is materially better than a bare CI approval stage: approvers and operators get AccessFlow's deployment list/detail, approvals queue, pipeline/environment administration, notifications, audit and version matrix. A general-purpose CI product is not required: Git can provide reviewed artifacts, and a small protected runner or job can poll AccessFlow, invoke the engine, and submit outcomes. The composition to compare is **Git + AccessFlow + runner/evidence** against **Git + CI + state + engine**. AccessFlow may replace custom approval/routing UI and some workflow state that the CI composition must own; it does not remove exact artifact/target admission, single-writer control, Oracle verification, or recovery. The runner is an execution component, not necessarily a separate user-facing platform. No observed staffing or maintenance measurements establish a net reduction.

| Is execution result verified by AccessFlow? | **No.** `EXECUTED` follows confirm-execution; outcome is reported by the caller. No per-target partial/unknown states. | Oracle compilation validity, effects, ledger consistency and accurate outcomes require runner-side verification and Oracle runtime evidence. |
| Does confirmation claim one exclusive runner? | **No.** The source has `@Transactional`, an optimistic `@Version` column and an already-`EXECUTED` idempotent success path; it does not issue a claim/lease or document exclusivity. | Runner must implement its own single-writer/admission mechanism. Repeated confirmation cannot be used as an exactly-one-run guarantee. |
| Does the version matrix prove what Oracle currently runs? | **No.** It is a projection of gated requests and reported outcomes. | Reconcile projection against Oracle/engine state before treating it as deployment truth. |
| Is AccessFlow API intrinsically simpler than CI fallback? | **No demonstrated net simplicity advantage.** It supplies more governance UI/workflow, while the difficult engine correctness, target inventory and recovery packages remain. | Existing CI entitlement/ownership and AccessFlow operational cost are not measured; final selection can revisit if an estate already operates AccessFlow or a platform assumption changes. |

These are contract findings, not Oracle runtime failures. AccessFlow deployment API is not classified as `FAIL` for Oracle SQL; it simply does not claim to execute or verify it. Oracle 19c/21c/26ai, RAC, TCPS, driver rights and the real estate remain outside this public-contract review.

## Evidence of concurrency and repeat confirmation

At c8bb, `DefaultDeploymentGateService.confirmExecution` is `@Transactional`. It loads the request, returns the detail view immediately when status is already `EXECUTED`, otherwise checks for `APPROVED`, evaluates the gate, and applies `EXECUTED`. `DeploymentRequestEntity` has JPA `@Version` on `version_lock`; the transition state service saves the changed entity. The code therefore supplies optimistic concurrency protection for competing status writes, not a durable execution claim with a holder, expiry, fencing token, or runner identity. The successful repeated-confirm path is explicitly idempotent. Consequently, `APPROVED` plus a green gate is a policy predicate and `EXECUTED` is a workflow transition; neither is proof that exactly one runner owns the right to write Oracle. The external engine must enforce that invariant.
